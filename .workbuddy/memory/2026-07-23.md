## 代码追踪：Hermes 是否有意图分析/子任务分解/子Agent调度阶段？
- 结论：**没有**。三个阶段全部隐式化，由 LLM 在对话循环中通过 tool call 完成。
- 实际流程：`build_turn_context()` prologue → `while` loop [LLM call → tool dispatch → repeat]

- 设计哲学：LLM IS the orchestrator — 无编排层，无预规划

## 设计决策分析：为什么选择 LLM-as-orchestrator 而非 pre-loop pipeline
- 六个核心原因：
  1. **Prompt cache 神圣不可侵犯**（最重要）：pre-loop 编排需要额外 LLM 调用 → 不同 prompt → cache miss；注入结果破坏 prefix。单循环 = 1 prompt, 1 cache, 0 miss
  2. **简单任务零开销**："2+2=?" 不需要意图分析；pipeline 增加 1-2 次 API 往返
  3. **窄腰保持窄**：编排层 = 核心代码，随每次 API 发送，需维护测试版本化；隐式 = 零核心 footprint
  4. **自适应非刚性**：刚性 pipeline（analyze→decompose→dispatch）分析错误则全盘错误；自适应 LLM 可随时纠偏
  5. **面向未来**：硬编码 pipeline 赌当前结构永远最优；模型改进 → 自编排免费提升
  6. **Kanban 例外证明规则**：kanban_decompose.py 确实做分解，但仅在无人 in-loop 的批量/自动化场景；chat 有人 in-loop → 自适应胜出
- 代码证据：system_prompt.py:530-540 "system prompt is stable across all turns... maximizing prefix cache hits"
- 代码证据：system_prompt.py:290 警告某些模型 "replies with plans instead of executing"
- 代价：弱模型可能跳过该做的规划；调试更难（无显式规划轨迹）
- 缓解：todo 工具结果在上下文压缩后重新注入；system prompt 反对纯计划回复

## 跨项目对比：OpenCode / Claude Code / Devin 是否也用 LLM-as-orchestrator
- 结论：**是**。主流 AI coding agent（OpenCode、Claude Code、Cursor、OpenHands、Aider）全部使用 ReAct 单循环设计
- 证据：
  - OpenCode `session/prompt.ts` 的 `while(true)` 循环：Reason → Act → Decide，退出条件为 finishReason !== "tool-calls"
  - OpenCode 的 "agents" 是配置模板（Build/Plan/General/Explore/Scout），非多 Agent 编排系统
  - Claude Code 的 subagents 有意限制：只回答问题，不写代码，不与主 agent 并行
  - Anthropic "Building Effective Agents" (2024-12) 明确区分 Workflow（预定义路径）vs Agent（LLM 自主导向），推荐"最简方案优先"
  - 行业共识："几乎所有2025-2026年能打的 Coding Agent 底层都逃不出 ReAct 模式"
- 唯一例外：Devin（Cognition）倾向多 Agent + 专用压缩模型，但即使 Cognition 也承认多 Agent 可靠性挑战
- 差异在工程层而非架构层：上下文管理策略、委派深度、安全机制、持久化方式
- Anthropic 谱系：Workflow（预定义）←→ Agent（LLM 导向），Hermes/OpenCode 在"纯 Agent"端，Devin 在"重型 Agent"端

## 用户追问：意图拆分 → 子Agent并行执行 → 聚合（Orchestrator-Workers 模式）
- 用户想了解：为什么不做"接受意图 → 拆分子任务 → 多子Agent并行 → 聚合"的默认模式
- Anthropic 框架将此命名为 "Orchestrator-Workers"，归类为 Workflow（非 Agent）
- **Hermes 已实现此模式**：
  - `delegate_task(tasks=[...], background=true)` 批量并行模式
  - `async_delegation.py:712 dispatch_fanout_batch()` — ThreadPoolExecutor 执行 fan-out
  - 一个 async slot 跑整个 batch，batch 内并行度受 `max_concurrent_children` 限制
  - 结果作为一条消息重新进入对话
- **但非默认模式**，四个工程原因：
  1. 上下文隔离：subagent 获"fresh conversation, no parent history"（delegate_tool.py:11），只看 parent 传的 context
  2. 写冲突：并行编辑同一文件 = merge conflict；tool 描述限定"parallel independent workstreams"
  3. 验证负担："subagent summaries are SELF-REPORTS, not verified facts"（delegate_tool.py:3428）
  4. 任务依赖：多数 coding 任务是顺序依赖链（read→understand→fix→test→verify），非 embarrassingly parallel
- 并行适用场景：research A+B、review N files、search M codebases；不适用：fix bug in auth module
- `max_spawn_depth` 默认 1（扁平），可配置为 2+ 启用嵌套 orchestrator
- `max_concurrent_children` 控制并行度上限
